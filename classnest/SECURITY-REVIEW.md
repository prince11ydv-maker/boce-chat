## Email production update · 6 November 2026

Existing account hashes, passwords, and sessions were preserved. The canonical state endpoint returned 200 with email enabled, and the browser recovery form was verified. Real reset and notification messages reached Gmail's inbox; verification mail reached Spam. Students should check Spam when waiting for verification.

Reset tokens contain 32 random bytes, are stored as SHA-256 digests, expire after 30 minutes, and are consumed atomically with the password update and session revocation. Normal password changes invalidate pending reset links. Request responses are generic and limited by IP and normalized address. Verification does not approve membership or enable subscriptions.

Email preferences default off. Only approved members/admins with verified mailboxes, a matching semester, and an enabled category receive individual notification emails. Consent is checked again before queued delivery; unsubscribe requires a signed link and explicit confirmation. Browser links keep tokens in fragments, remove them from history promptly, and consume them only on POST, so opening or scanning a link does not reset a password or change consent.

The durable outbox encrypts token-bearing payloads with AES-256-GCM under a separate server secret. Delivery runs after commit with leases and bounded retries; SMTP acknowledgements can be uncertain, so retries provide at-least-once semantics. Brevo Free permits 300 daily emails. The app caps counted attempts at 280 per UTC day, including no more than 180 notifications, and reserves queue capacity for recovery. The email migration is applied. ## Findings and applied remediation

| Finding in the starting version | Concrete impact | Applied remediation |
| --- | --- | --- |
| Local requests accepted arbitrary `Host` values while owner setup trusted a loopback socket | A hostile hostname rebinding to localhost could reach a fresh workspace's setup/API under its own browser origin | Accepted-host allowlist, exact browser-origin checks, cross-site fetch rejection, and hostile-host regression tests |
| Upload validation relied only on filename extension | A different payload could be renamed to an allowed document/image type and shared with classmates | Signature and UTF-8 checks, safe filenames, bounded Office ZIP/local-header checks, and forced sandboxed attachment downloads |
| The 700 MB quota counted attachment bytes only, and posting/registration had no durable row/text caps | Text notes, replies, registrations, or concurrent temporary uploads could exhaust storage or force very large state responses | Posting/record/text/session limits, existing orphan-file accounting, and reserved capacity for bounded concurrent uploads |
| Missing-user login skipped password hashing; duplicate signup responses disclosed existing accounts | Authentication responses could reveal whether an email was registered | Bounded equivalent password work, generic registration responses, and per-account/IP authentication throttles |
| Password work used synchronous scrypt | Repeated authentication work could block all readers on the same Node process | Asynchronous stronger scrypt with four concurrent authentication operations maximum; existing hashes migrate with a conditional update to prevent password-change races |
| Missing or malformed request bodies were not consistently validated | Invalid requests could become generic server errors instead of controlled client errors | Body/type validation, normalized client errors, safe error logging, and malformed-request tests |
| The Linux App Service template put SQLite on a network share | Unsupported locking could jeopardize durable class data even if the code deployment succeeded | **Unsafe templates removed; deployment script fails closed before resource creation**. A supported managed database integration and migration are still required |

No SQL injection, direct file-path traversal, stored browser-script injection, or role bypass was found in the reviewed starting routes. SQL values were parameterized, storage filenames were generated by the server, rendered user text was escaped, and posting/admin permissions were checked server-side. This statement is limited to the reviewed code paths.

## Original local verification and current limits

The five isolated integration/security test suites passed after backend hardening. They cover class CRUD/persistence, hostile hosts/origins, malformed bodies, non-disclosing signup, file/Office validation, ownership, upload limits, session rotation/caps, owner-setup races, legacy-password migration, account throttling, and production setup/cookies. An independent final source re-read found no additional actionable authentication/role bypass in those paths. The Azure deployment guard was also exercised locally and stopped before Azure CLI calls or resource creation. No Azure account was accessed or provisioned.

- File signature/container checks **are not antivirus scanning** and do not establish that a document is harmless. Downloaded Office/PDF content still needs appropriate caution.
- Accounts use custom email/password sign-in. The new email flow verifies mailbox ownership, while admins still approve classmates they recognize. Verification never grants posting access.
- Password recovery and email delivery are deployed and checked as described above, including an automatic retry-worker run. Multifactor authentication and a dedicated security-monitoring service are not configured.
- The current SQLite database is for a single local server. Keep private database snapshots and matching upload-directory backups. Do not share backups publicly or put this database on an unsupported network filesystem.
- Full semester state is still loaded in one response. Content/record bounds limit growth, but a large class needs pagination and load testing before scaling.
- There is no live Azure deployment. The website uses Vercel Hobby and Supabase Free; keep checking their usage and free-plan quotas.
